# 万人阵 · 性能规划与快进系统

实测机器：i9-9980HK（8 核 16 线程，2.4 GHz），macOS，`-O3 -march=native`。
命令：`./build/wanren_bench plain 1500 <线程> 1 <人数倍率>`，1500 tick（2.5 分钟战场时间，含接敌）。

### v0.2（第一、二步做完）

| 人数 | 线程 | ms/tick | 网格 | 士卒并行 | 士气+统计 | 每人每 tick | 相对 v0.1 |

| 19 400 | 16 | **0.78** | 0.18 | 0.46 | 0.15 | 40 ns | **2.5×** |
| 48 500 | 1 | 8.84 | 0.42 | 7.00 | 1.42 | 182 ns | 1.3× |

| 97 000 | 1 | 18.11 | 0.86 | 14.48 | 2.77 | 187 ns | 1.4× |
| 97 000 | 16 | **3.63** | 0.85 | 2.13 | 0.64 | 37 ns | **2.4×** |

做了什么：
- 网格按**活人包围盒**重建（格数从世界 3000×3000 m 的 56 万格降到战场实际范围的几万格），排序时顺便生成 16 字节 `Packed{x,y,idx,unit,side,state}` 连续数组，邻居扫描只读它。
- 线程池改成**按块动态领取**（原子计数器），所有跨士卒的写入按块编号缓冲、按块顺序串行应用 → 结果与线程数无关（测试第 1 项仍过）。
- 士卒阶段按**网格顺序**分块（1024 人一块），邻居都在缓存里。
- 士气 + 统计合并成一次并行遍历（2048 人一块，每块一份每曲累加器，块序归约）；溃走事件按块缓冲后串行应用。
- 每 tick 预计算曲级速度表与最近敌曲距离；`hypotf` 全换 `sqrtf`。
- 试过把网格重建并行化（原子计数 + 格内排序）：前缀和与原子开销把收益抵消，反而慢，已回退为串行。

剩余瓶颈（10 万人 16 线程 3.63 ms）：串行网格 0.85、士卒并行 2.13（1→16 线程 6.8×，仍是带宽限制）、串行的曲级后处理 0.4 左右。下一步见第三步「跳过不需要算的人」。

快进实测（界桥 2.15 万人，模拟线程 + 渲染 64 fps）：×1 实际 ×1.0，×16 实际 ×16.0，最快档实际 **×89**。

## 2. 目标

| 规模 | 目标 ms/tick（16 线程） | 能支持的快进倍率（10 Hz 模拟） |
|---|---|---|
| 2 万 | ≤ 0.6 | ×150 |
| 5 万 | ≤ 1.5 | ×60 |
| 10 万 | ≤ 3.0 | ×30 |

依据：把串行段并行化（−4 ms）、并行段做缓存友好与跳过（×2–3），10 万人从 8.6 降到 3 以内是保守估计。

## 3. 优化路线（按收益 / 代价排序）

### 第一步：串行段并行化（预计 10 万人 −4 ms，代价一天）
- `moraleAndRout` + `updateUnitsPost` 合并为一次 **parallelFor**：每线程一份「每曲累加器」（在阵数、在槽数、士气和、疲劳和、逃走数），结束后归约。
- 溃走判定仍在并行里做（只写自己的 state 和 morale），但「同伍连坐」「网格逃走计数」这些**写别人**的操作改成往每线程事件缓冲里记，事后串行应用（溃走事件每 tick 通常几十个，串行很快）。
- 网格重建：计数阶段改每线程直方图 + 前缀和，散布阶段用每线程偏移；或者更简单：**两 tick 重建一次**（士卒每 tick 最多走 0.7 m，格 4 m，隔一 tick 的网格误差可以接受——近邻半径按 +1 m 放宽）。

### 第二步：并行段缓存友好（预计 ×2，代价一到两天）
- **按格遍历，不按下标遍历**：线程分到的是网格的行带，处理一格时它的 3×3 邻格刚被摸过、都在 L1/L2 里。
- **邻居热数据打包**：网格排序时顺便生成 `packed[k] = {x, y, side|state, unit}`（16 字节），按格顺序连续；邻居扫描只读这一条数组。
- `hypotf` 全部换 `sqrtf`，分支外提（士卒的速度上限、触及距离在曲一级算好，查表）。
- 线程池改**动态分块**（原子计数器领 64 格一块），接敌带集中在少数行时不至于让一个线程扛全部。

### 第三步：跳过不需要算的人（预计再 ×2，代价半天）
- 每格维护「3×3 邻格里有没有敌人」位（从每格每方计数直接得出，O(格数)）。**没有敌人的格**里的士卒不做找敌，只做追槽位 + 分离；在槽位内且曲的凝聚 > 0.9 的人连分离也跳过（他们本来就不会撞到谁）。会战中 80% 以上的人处于这种状态。
- 溃走者只在每 3 tick 找一次逃跑方向。
- 齐射改为**分摊到后续 10 tick** 执行（每 tick 发十分之一的箭），既消掉尖峰，画面上也更像持续的箭雨。
- AI 议定按曲轮转（每 tick 议几曲），不要一次全议。

### 第四步（需要时才做）：SIMD 与 50 万人以上
- 分离 / 追槽位是逐分量的浮点运算，可以 8 路 AVX2 一次算 8 个士卒（SoA 布局已经为此准备好）。
- 邻居比较改成「格对格」的小矩阵（格 A 的 n 人 × 格 B 的 m 人），内层循环向量化。
- 超过 50 万人时，内存 20 MB 以上超出 L3，要按空间分块（tile）调度线程让工作集留在 L2。

不做的事：GPU 计算（把逻辑搬到 compute shader 会让士气、溃散这类分支逻辑和可复现性都变难，而 CPU 这条路到 50 万人都够）。

### 验收
每一步做完都跑：`wanren_test`（复现性必须保持：同种子任意线程数逐人一致），再跑上面三档规模 1 / 16 线程的 bench，把表格更新到本文第 1 节。

## 4. 快进速度系统

### 现状的问题
- 模拟和渲染在同一线程：每帧先补 tick 再画。倍速上限由「每帧最多 64 tick」硬限，超过就把累积时间**清零**——高倍速下时间被悄悄丢掉，显示的倍率不是真的。
- 高倍速下每帧仍插值、仍画全部 HUD，浪费。

### 设计
1. **模拟独立线程**。模拟线程按目标节奏跑 tick（速度 ×N → 每秒 10N tick；「最快」档不限速、跑满），渲染线程 60 fps 自己转。两者之间用**三缓冲快照**：模拟每 tick 结束把渲染需要的数据（x、y、state、side|kind|flags 打包、曲摘要、纪事、箭矢）拷到一个空闲缓冲并标记为最新；渲染取最新的那个。拷贝 10 万人约 1.2 MB，< 0.3 ms。
2. **档位**：暂停、单步（逐 tick，看细节）、×0.5、×1、×2、×4、×8、×16、×32、最快。HUD 显示「目标 ×16 · 实际 ×14.8」——实际倍率 = 最近一秒的 tick 数 / 10，诚实告诉玩家机器跟不跟得上。
3. **高倍速降画质**：≥ ×8 时关插值（直接画最新快照），曲标签和箭矢只在 ≤ ×4 时画，纪事面板每 0.5 s 刷一次。
4. **命令线程安全**：玩家命令进一个无锁队列，模拟线程在每 tick 开头取出来 `issue`；命令延迟仍按战场时间计，所以快进不改变旗鼓延迟的「秒数」。
5. **跳到事件**：「快进到接敌 / 到下一次齐射 / 到有曲溃」——模拟线程以最快档跑，直到条件满足自动回到 ×1。这是 AI 对 AI 观战和调平衡最常用的功能。
6. **批量推演**不走渲染：`wanren_bench` 已经是无渲染的最快档；以后加「N 局不同种子」统计（胜率、时长、伤亡分布），与主仓库的 `npm run sim` 对应。

### 实现状态（v0.2）
已做：模拟线程 + 快照池（`app/simthread.hpp`）、命令队列、档位（暂停 / 单步 `.` / ×0.5–×32 / 最快）、HUD 显示目标与实际倍率、≥ ×8 关插值与箭矢标签、跟不上时丢弃积欠不追。
未做：「跳到事件」自动回 ×1；批量多种子统计。
